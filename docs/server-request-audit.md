# sub2api 请求与缓存检查

## 结论与适用范围

单后端进程内，同账号、同通道、同查询范围的请求共享缓存与进行中的任务；设备、登录会话、页面和手动刷新不会绕过间隔。缓存过期本身不发请求，没有后端轮询或后台重试。

这里的间隔不是全实例每 N 秒只能发送一次 HTTP 请求。不同账号、通道、日期范围、时区及用户筛选是不同查询；目录分页和旧版额度接口回退也是一次读取中的多个步骤。所有真实 HTTP 请求共享最多 4 个并发槽。

关闭所有页面后不再开启新的刷新轮次。关闭前已经被服务端接受的一轮有限工作可以完成，不会因某一个设备断连而取消其他设备共同等待的请求。单 HTTP 请求含排队有 20 秒超时，多步骤入口传递同一个 30 秒超时信号；过期的排队请求不会开始网络请求。这不是“最后一台设备关闭的瞬间强制中断所有在途请求”。

## 全部上游路径

真实网络请求唯一入口是 `server/upstream.ts` 的 `fetch`；调用均来自 `server/monitor.ts`。`server/index.ts` 为当前实例创建一个 Monitor，并由所有 API 请求共用。

以下路径相对于 `/api/v1/admin/`：

| 上游请求 | 间隔 | 共享粒度及行为 |
| --- | --- | --- |
| `GET accounts` | 固定 60 秒 | 整份目录；分页完成后才缓存，分页失败进入退避 |
| `GET accounts/:id` | 状态间隔，默认 5 秒 | 账号 ID；状态、额度、消费入口共用 |
| `POST accounts/today-stats/batch` | 状态间隔，默认 5 秒 | 逐账号缓存，只请求缺失或过期账号；跨日不重置间隔 |
| `POST accounts/usage/batch` | 额度间隔，默认 30 秒 | 逐账号缓存，重叠批次去重，始终 `force=false` |
| `GET accounts/:id/usage` | 同一额度缓存 | 批量接口 404/405 时回退，记住兼容状态；始终 `force=false` |
| `GET users?role=admin` | 消费间隔，默认 15 秒 | 全实例共用完整 Admin 名单，分页校验，失败不回退为含 Admin 的消费 |
| `GET usage/stats` | 消费间隔，默认 15 秒 | 账号、起止日期、时区、用户 ID；总计使用空用户 ID，跨 Admin 开关共用 |

`usage/stats` 保留 `nocache=true` 以明确读取上游当前统计；发送频率由应用自己的共享缓存约束。今日和周期消费日期相同时共用同一次原始读取。成本、续费日中不改变查询日期范围的变化，不会重复请求原始消费。

## 本次发现与修复

1. **Admin 开关重复读取总计**：原来最终结果按开关隔离，两个设备采用不同口径时会重复查询同一总计。现按真实上游参数缓存原始总计和小计，再计算对应结果；计算层不附加第二层 TTL。
2. **跨日突破今日统计间隔**：原来日期进入今日统计缓存键，午夜可立即重查相同接口和账号。现限流键保持账号 ID，数据另附统计日期；新的一天暂不展示昨日值，等待间隔结束后按需查询。
3. **失败后调大间隔仍提前重试**：原来失败只检查旧退避。现从每次成功或失败完成时计算新间隔，同时保留已有退避，两个期限都满足才允许查询。
4. **429 未遵循上游冷却**：现支持 `Retry-After` 的秒数和 HTTP 日期；无有效值时默认 30 秒。冷却覆盖同一上游连接的所有路径和排队请求，缓存也保留这一期限；没有定时恢复请求。
5. **排队工作过期后仍进入 fetch**：现在取得并发槽后再次检查取消信号和 429 冷却。已取消的队列项会移除，释放槽位后可继续正常处理后续请求。
6. **缓存淘汰保护不足**：清理只发生在容量压力下，保留正在执行、当前批次引用、仍在间隔或退避中的键；即使未来增加超过 10 分钟的间隔也不会提前淘汰。无法安全腾出容量时拒绝新增范围。
7. **过期账号状态触发依赖查询**：账号状态失败时不再基于旧状态发起额度或消费查询；相关入口共享贯穿多步骤的超时信号。

## 缓存策略

- 间隔从上游读取完成时起算；缓存命中不延长原始样本有效期。
- 同一键先同步登记进行中的 Promise，再执行异步读取；并发及重叠批次只读取一次同账号数据。
- 不使用 stale-while-revalidate 或后台定时刷新。到期后的下一次客户端请求负责读取，并等待结果。
- 失败指数退避最长 10 分钟；429 指定的更长期限优先。失败保留同范围最后成功数据及原更新时间，并返回错误；首次失败不补零。
- 消费保留最后一次完整计算，依赖失败不将部分新旧结果混算成成功值；结果时间取最旧的依赖样本时间。总计和各用户小计不是原子快照，负数或缺失结果按错误处理。
- 今日统计跨日隐藏旧值；消费显式改变日期范围时使用另一缓存键。用户改变时区或续费日造成查询范围变化时，可以产生新查询。
- 各缓存最多 5000 个键；仅按需清理至少 10 分钟且已结束冷却的旧键。缓存不持久化到磁盘或 Service Worker。

## 验证

Vitest 共 57 项通过，其中新增 14 项；类型检查、生产构建和 Lint 通过。

- 20 客户端并发访问全部数据入口，分别验证 5 秒、15 秒、30 秒边界和目录缓存。
- 两个独立登录会话、连续手动刷新，不能通过请求体中的 `force` 绕过间隔。
- 重叠账号批次、目录分页失败、旧版额度回退、跨日和动态间隔修改。
- Admin 开关之间共享总计、跨页面共享今日消费、投影不叠加 TTL、失败保留完整结果。
- 429 两种 `Retry-After` 格式、实例统一冷却、排队取消与并发槽恢复。
- 假时钟推进 7 天，无新客户端调用时没有增加上游调用，也没有轮询定时器。

验证使用可计数的上游替身与传输层 fetch 替身，没有访问真实 sub2api 实例。实际部署版本、网络延迟和上游自身缓存仍需连接真实实例后验收。

## 部署边界

多客户端共享的前提是访问同一个应用进程。多个进程、多个容器或多个独立预览实例之间不共享缓存、限流和 429 冷却。进程重启会清空这些内存状态，下一次访问可立即重新读取。需要多副本或跨重启保留限流时，应改为共享存储及分布式请求协调；当前按单进程部署。
